# 개발 컨벤션

쏙톡(Sock-Talk) · 팀 모루 · 저장소의 `docs/convention.md`에 두는 문서입니다.

## 1. 기본 원칙

- **"반드시 구현" 기능을 먼저 완성**합니다. "추가시" 기능은 필수 기능이 모두 동작한 뒤에 시작합니다.
- 담당 파트(서버 / 클라이언트)를 넘어서는 수정은 상대방에게 먼저 알립니다.
- 모든 소스와 문서는 **UTF-8**, 줄바꿈은 **LF**입니다.

## 2. 담당 영역

| 영역 | 담당 | 비고 |
|---|---|---|
| `src/socktalk/server/` | 박지수 | |
| `src/socktalk/client/` | 정채원 | |
| `src/socktalk/common/`, `docs/protocol.md` | 공동 | 변경 시 상대방 확인 필수 |
| `docs/`, `README.md` | 공동 | |
| `main` 브랜치 병합 | **박지수만** | |
| 관리자 화면 | 박지수 | |

## 3. 브랜치 규칙

| 브랜치 | 용도 |
|---|---|
| `main` | 제출용. 실행 가능한 상태만 유지. **박지수만 병합** |
| `dev` | main의 서브브랜치(이름은 팀 합의로 변경 가능). 작업 브랜치의 병합 대상 |
| `feature/<이슈번호>-<파트>-<기능>` | 새 기능 (예: `feature/1-server-login`, `feature/client-chat-ui`) |
| `fix/<이슈번호>-<파트>-<내용>` | 버그 수정 |
| `docs/<이슈번호>-<내용>` | 문서 수정 |

- 브랜치 이름은 영문 소문자와 하이픈만 씁니다.
- `main`과 `dev`에는 직접 push하지 않고 반드시 PR을 거칩니다.

## 4. PR · 이슈 흐름

1. 기능 한 줄을 **이슈 하나**로 만듭니다. 라벨은 `must`/`추가시`, `server`/`client`를 붙입니다. 추가 기능은 제목에 `[추가시]`를 붙입니다.
2. 작업 브랜치를 만들어 구현하고 커밋합니다.
3. `dev`를 대상으로 PR을 만듭니다. PR에는 이슈 번호를 적습니다. (`Closes #12`)
4. **CI/Validate와 CodeRabbit 검사**를 확인하고, 지적 사항을 고치거나 답변합니다.
5. 이상이 없으면 **작성자가 본인 담당 파트에 한해 직접 `dev`에 병합**합니다. 병합 방식은 **Squash and merge**입니다.
6. 병합 후 **작성자가 이슈를 직접 close** 합니다. (기본 브랜치가 아닌 곳에 병합하면 `Closes` 키워드로 자동 close되지 않을 수 있으므로 직접 확인합니다.)
7. 마일스톤 단위로 `dev`가 안정되면 **박지수가 `main`에 병합**합니다.

**병합 전 체크리스트**

- [ ] 담당 영역 안의 수정인가 (공용 파일이면 상대방 확인을 받았는가)
- [ ] CI/Validate 통과, CodeRabbit 지적 사항 처리
- [ ] 서버와 클라이언트를 실제로 실행해 확인했는가
- [ ] 비밀번호 등 민감 정보와 빌드 산출물이 커밋에 없는가

## 5. 커밋 메시지

형식: `타입(범위): 내용`

| 타입 | 용도 |
|---|---|
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `docs` | 문서 |
| `refactor` | 동작은 같고 구조만 정리 |
| `style` | 포맷, 이름 정리 |
| `chore` | 설정, 라이브러리 |

범위는 `server`, `client`, `common`, `docs` 중 하나입니다.

- 예: `feat(server): 부서별 단체방 자동 입장 구현`
- 예: `fix(client): 말풍선 너비 계산 오류 수정`
- 제목은 50자 이내로 쓰고, 한 커밋에는 하나의 변경만 담습니다.
- 추가 기능은 `feat(server): [추가시] 금칙어 필터링 구현`처럼 표시합니다.

## 6. Java 코드 컨벤션

**이름**

| 대상 | 규칙 | 예 |
|---|---|---|
| 패키지 | 소문자 | `socktalk.server` |
| 클래스 | PascalCase | `ClientHandler` |
| 메서드·변수 | camelCase | `sendMessage` |
| 상수 | UPPER_SNAKE_CASE | `DEFAULT_PORT` |
| 화면 클래스 | `~Frame`, `~Panel`, `~Dialog` | `LoginFrame` |

**형식**

- 들여쓰기는 스페이스 4칸, 한 줄은 120자 이내입니다.
- 파일 하나에 클래스 하나를 둡니다.
- `import *`는 쓰지 않고, 쓰지 않는 import는 지웁니다.
- 중괄호는 한 줄짜리 `if`에도 씁니다.

**주석**

- 한글로 써도 됩니다. 코드를 읽으면 알 수 있는 내용은 쓰지 않고, **이유**를 씁니다.
- 할 일은 `// TODO(지수): 내용`처럼 담당자를 적습니다.
- 공유 자료를 지키는 락에는 "무엇을 지키는지" 주석을 남깁니다.

## 7. 구조 규칙

- 화면 코드는 소켓을 직접 다루지 않습니다. 호출 순서는 `ui → ConnectionManager → Protocol`입니다.
- 서버 코드는 Swing을 import하지 않습니다. (단, server/admin/만 예외로 허용)
- 서버와 클라이언트가 함께 쓰는 값(메시지 타입, 포트)은 `common/Protocol.java`에만 둡니다.
- 색상과 폰트는 `client/Theme.java`에만 둡니다.

## 8. 스레드 · 동기화 규칙

- 소켓 읽기는 전용 수신 스레드에서 합니다. 클라이언트는 받은 메시지를
  `MessageListener`로 전달하고, 화면은 `SwingUtilities.invokeLater()` 안에서만 수정합니다.
- 같은 소켓에 여러 스레드가 쓰는 `send()`는 `synchronized`로 감쌉니다.
- 연결 끊김(`readLine()`이 null이거나 IOException)은 오류가 아니라 정상 처리 경로이며,
  `finally`에서 접속자 목록 제거와 퇴장 메시지 처리를 합니다.

## 9. 예외 · 자원 · 로그

- 소켓과 스트림은 `try-with-resources` 또는 `finally`에서 닫습니다.
- 빈 `catch` 블록을 두지 않습니다. 무시하는 경우 이유를 주석으로 남깁니다.
- 로그는 `System.out.println`이나 `printStackTrace()` 대신 `java.util.logging.Logger`를 씁니다.
- **비밀번호는 로그에 출력하지 않습니다.**
- 클라이언트의 비정상 종료(연결 끊김)는 오류가 아니라 정상 처리 경로입니다. 목록에서 제거하고 퇴장 메시지를 보냅니다.
- 관리자 기능의 계정 추가·부서 변경도 `synchronized`와 임시 파일 교체 방식을 따릅니다.

## 10. 프로토콜 규칙

- 메시지는 한 줄이 하나이고, 형식은 TYPE|값1|값2, 인코딩은 UTF-8입니다.
- 모든 필드는 `Message.encode()` / `Message.decode()`로만 만들고 해석합니다.
  (`|`, `\`, 줄바꿈은 이스케이프되므로 코드에서 `|`를 직접 붙이거나 자르지 않습니다.)
- 타입 문자열은 `Protocol.java` 상수로만 사용합니다.
- 파일 전송은 제어 채널이 아닌 별도 파일 소켓(`FILE_PORT`)과 DataInputStream/DataOutputStream을
  사용합니다. (순서는 protocol.md 7번 참고)

## 11. "추가시" 기능 표시 규칙

PDF의 "추가 시" 기능(다른 사원 정보 조회, 즐겨찾기, 금칙어 필터링)은 **필수 기능 완료 후**에 구현합니다.

- 코드에는 `// 추가시: 기능 이름` 주석을 붙입니다. 검색 한 번으로 위치를 모두 찾을 수 있게 문구를 통일합니다.
- `Protocol.java`는 `// ===== 필수 =====`와 `// ===== 추가시 =====` 구역으로 나눕니다.
- 미리 올려 둔 빈 파일이나 껍데기 클래스를 만들지 않습니다. 구현을 시작할 때 파일을 만듭니다.
- UI에서 자리만 잡아 둘 때는 `setVisible(false)`로 숨기고 `// 추가시: 구현 후 true로 변경`을 남깁니다.

## 12. 디자인 상수 (Theme)

| 이름 | 값 | 용도 |
|---|---|---|
| `BG` | `#E5E8E2` | 창 배경 |
| `SUB` | `#CDE4E3` | 보조 영역, 선택 행 |
| `ACCENT` | `#3AABD1` | 강조 (선, 아이콘, 상태 표시) |
| `PRIMARY` | `#668CAF` | 주요 버튼, 내 말풍선 |
| `TEXT` | `#1F2A36` | 본문 글자 (제안값) |
| `TEXT_ON_COLOR` | `#101820` | 주요색·강조색 위의 글자 (제안값) |

- 폰트는 맑은 고딕으로 통일합니다.
- `PRIMARY`와 `ACCENT` 위에는 **흰 글자를 쓰지 않습니다.** 대비가 낮아 작은 글자가 읽기 어렵습니다.
- 위 두 글자 색은 팀에서 합의한 값이 아니라 제안값이므로, 화면을 만들며 확인하고 조정합니다.

## 13. 파일 · 보안 규칙

- 빌드 산출물(`bin/`, `*.class`), IDE 설정, 로그, 전송 받은 파일 폴더는 `.gitignore`에 넣습니다.
- `data/accounts.txt`에는 **테스트용 가짜 계정만** 넣습니다.
- 서버가 계정 파일을 수정할 때는 `synchronized`로 감싸고, 임시 파일에 쓴 뒤 교체해 저장 중 종료돼도 원본이 깨지지 않게 합니다.
- 발표용 jar는 저장소에 올리지 않고 GitHub Releases에 올립니다.

## 14. 테스트 기준

기능을 병합하기 전에 아래를 직접 확인합니다.

- 클라이언트 3개 이상을 동시에 실행해 채팅, 접속자 목록이 맞는지
- 클라이언트를 강제 종료했을 때 서버가 계속 동작하고 퇴장 메시지가 나가는지
- 서버를 끄면 클라이언트가 멈추지 않고 안내 후 종료되는지
- 한글 닉네임과 이모티콘이 깨지지 않는지
- 부서 이동 시 접속 중인 사용자 처리
- 방 만들기 후 목록 갱신
- 활동상태 변경이 다른 접속자에게 반영되는지
